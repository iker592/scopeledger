# Is this a revision or a new request?

A request can sound small while changing the deliverable. The useful distinction is the agreement you already made, not the number of minutes the client thinks it will take.

Start with the existing baseline: pages, functions, content responsibilities, review rounds and acceptance criteria. Then write the request in one sentence. Compare the request with a specific baseline item.

An example baseline might include a five-page website, one contact form and two design-review rounds. Correcting a form that does not submit would normally be correcting the agreed work. Adding a booking calendar introduces a new function. A sixth page is another deliverable. A third review round depends on how review rounds were defined and agreed.

Avoid using the label “out of scope” as the whole explanation. Show the reference:

“The agreed deliverables include one contact form. This request adds a booking calendar with availability rules and confirmation emails.”

If the original description was ambiguous, acknowledge that ambiguity. Do not retroactively invent an exclusion. Clarify the desired result, estimate the work, and agree on how to handle it. Sometimes the right choice is a paid addition, a swap, phase two, or an explicitly recorded courtesy.

Before doing the work, capture the decision in writing. A change order should describe the extra work, price, timing and approval. Calling something a change does not make it approved or paid.

Worksheet:

- Existing scope reference: [specific page/function/round]
- New request: [one sentence]
- Resulting deliverable: [what the client will receive]
- Decision: [included / correction / paid addition / swap / defer / courtesy]
- Reason: [plain explanation]
- Fee and timing: [amount / date effect]
- Approval needed before starting: [who / how]
